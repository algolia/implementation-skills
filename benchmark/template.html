Implementation skills benchmark ·

There is no best model.
There is a best pairing.

Same task, same seeded store, same brief — run with and without the Algolia implementation skills, then blind-graded against the live index. Below: every pair, what each model did with the skills, and which one to run them on.

Which model should run the skills?

The skills are instructions. How much they help depends on whether the model can execute what it reads — and whether it verifies what it wrote. Three tiers, three different answers.

Read this as direction, not a ranking. The mid-tier row has seven pairs behind it; the top and small tiers have one or two per task. Enough to see the shape, not enough to separate two models by a point.

How it's built

The design borrows from Algolia's Agentic Search Leaderboard: score what the agent actually does against live state, never what it says it did.

A real store, seeded300-product catalog on a dedicated Algolia app. For audits, 16 planted defects — most of them symptom-free.
Identical briefs, pinned modelByte-identical prompts per pair. One model per pair, pinned. "Add search to our store, make it good." — or "audit this."
Two arms, one differenceBare: client library, REST, public docs. Skills: the same plus the implementation skills and the CLI. Nothing else changes.
Live checks, blind gradersTen deterministic checks against the live index per run, then a 35- or 37-point rubric scored by a condition-blind grader told to ignore toolchain.
Claims verified, not readEvery scored claim is checked against live state — settings, queries, the rendered page, captured event payloads. Unsupported claims score zero.

What the skills change

On the recommended tier, the gap is not "smarter code." It is a different definition of done.

3/3 vs 1/3

Analytics wired and verified. From a one-line brief, the skills arm shipped attributed click and conversion events every time. The bare arm shipped them once — twice it deferred them as "out of scope."

7.3 vs 4.3/10

Silent defects fixed on an existing store. Tie-breakers, searchable facets, hierarchy, facet stats, leaked internal fields — the class of issue that never throws an error and never fails a demo.

9/10 from 4/10

After the fixes, unprompted. The benchmark found the skills weren't being invoked; we shipped algolia-audit and routing fixes; the free-choice re-run invoked it on its own and fixed 9 of 10.

Methodology, limitations, updates

Controls and scoring

One Algolia application, one 300-product catalog (seeded, deterministic), one brief per task type. Each pair pins one model and runs the same brief twice: bare (client library, REST API, public docs) and skills (the same plus the implementation skills and the Algolia CLI). Prompts are byte-identical within a pair.

Two scoring layers. Live checks: ten deterministic assertions against the live index and rendered page after each run (settings shape, facet stats present, replicas actually sorted, retrieval hygiene, page renders, events captured). Blind rubric: 35 points for builds, 37 for audits, scored by a grader that does not know which arm it is grading and is instructed to verify every claim in the agent's write-up against live state. The two rubrics are never pooled.

What "working storefront" means

After each run the page is loaded in a browser. It counts as working if search requests fire, hit cards render with readable text, and there are no uncaught errors. Several runs on the small tier shipped pages that passed every settings check and rendered nothing — a wrong CDN filename for the Insights loader, or a seeded crash left in place — which is why this column exists and why the release-qa skill now has a mechanical page-smoke gate.

Known limitations
  • Sample size. Seven pairs on Claude Sonnet 5; two counted on GPT-5.6; two on Haiku 4.5; one on Opus 5. Variance runs both ways at this n — one adverse pair calibrates a pattern, it does not reverse it, and one favorable pair does not establish one.
  • One catalog, one vertical. Ecommerce only. Support, B2B and marketplace catalogs are the obvious next seeds.
  • Timing is agent time. Wall-clock and tokens as reported by the agent harness; Codex does not expose tokens. Skills cost more time in most pairs (typically +30–40%, up to +65% on Opus) — this benchmark measures correctness, not speed.
  • Graders are models. Condition-blind and told to verify against live state, with deterministic checks as a floor. Disagreements between grader and checker were resolved by re-checking live and are noted in the pair notes.
  • Platform and model are confounded on Codex. GPT-5.6 was only run through Codex; a second Codex model would separate the two.

Update policy and changelog

Every run is appended to benchmark/data.json with its date, model, mode, both arms' scores, effort, storefront outcome and the grader's decisive note; this page recomputes on build. Excluded runs stay in the data with a reason. Corrections restate the affected pair and are listed here.
